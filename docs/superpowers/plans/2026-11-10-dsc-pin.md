# DSC Pin Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the Microsoft365DSC pin to 2.26.1104.1, and add a pipeline that bumps the pins on request, by pull request, from a typed version number.

**Architecture:** `src/PolicyEngine/Data/Versions.psd1` is the single source of the pinned versions; the module (`Get-PEPinnedVersion`), `tools\Export-M365DscTenant.ps1` and `pipelines\scripts\Install-PipelineDependencies.ps1` read it, and a blueprint records the version it was built with (a mismatch is refused). So the bump pipeline changes only that file, on a branch, and opens a pull request; it never changes `main` directly and never overrides a pin at run time (the guard needs exports, compares and applies to agree on one version).

**Tech Stack:** PowerShell 7.6, Pester 5.7.1 (`tools\Invoke-PETests.ps1`), Azure DevOps YAML, Azure DevOps REST.

**Spec:** none (maintenance). Evidence: Microsoft365DSC issue 7563 (SC through the LCM) was closed by PR 7571, released in 2.26.1028.1; 2.26.1104.1 is the latest release. Process: `docs/handover.md`, "When the Microsoft365DSC pin changes".

## Global Constraints

- The pin lives only in `src/PolicyEngine/Data/Versions.psd1`; nothing else is edited to move it except tests and fixtures that name the version literally.
- Historical text stays as it is: `docs/handover.md` sections about earlier versions, and comments such as `tests/ExportLog.Tests.ps1:382` that record what an older version did.
- `data\` is git-ignored local data: never touched.
- No secret anywhere; the bump pipeline's only writes are a branch and a pull request, never `main`.
- Run tests with `pwsh -NoProfile -File tools\Invoke-PETests.ps1 -Path <file> -Fast` (one file per call); run everything without `-Fast` before the last commit of a task. Do not write log files outside the worktree.

## Review Focus

- A version that is not a four-part number is refused before anything is touched. Task 2.
- A version the PowerShell Gallery does not have gives a clear message and changes nothing. Task 2.
- The version already pinned is "nothing to do": no branch, no pull request. Task 2.
- The edit replaces only the value on the pin line: comments, the other pin and line endings survive; the result still parses with `Import-PowerShellDataFile`. Task 2.
- A pull request for the same version already open (branch `dsc-pin/<version>` exists) is not duplicated. Task 2.
- A downgrade is allowed but says so loudly (the message and the pull request contain `DOWNGRADE`). Task 2.

### Task 2: Pipeline that bumps the pins by pull request

**Files:**
- Create: `pipelines/scripts/Update-DscPin.ps1`, `pipelines/Bump-Dsc-Pin.yaml.template`
- Modify: `pipelines/README.md`
- Test: `tests/UpdateDscPin.Tests.ps1`, `tests/PipelineYaml.Tests.ps1`

**Interfaces:**
- Produces: `pipelines\scripts\Update-DscPin.ps1 -Version <string> [-GraphAuthenticationVersion <string>] [-PinPath <string>] [-SkipGalleryCheck] [-CreatePullRequest]`.
  - `-Version` must match `\A\d+\.\d+\.\d+\.\d+\z`; `-GraphAuthenticationVersion` must match `\A\d+\.\d+\.\d+\z` (empty leaves that pin alone).
  - `-PinPath` defaults to the repo's `src\PolicyEngine\Data\Versions.psd1`.
  - Without `-CreatePullRequest` it only edits the file and prints `Microsoft365DSC <old> -> <new>` (and the same for Graph when changed).
  - With `-CreatePullRequest` it then creates branch `dsc-pin/<version>`, commits, pushes, and opens a pull request into the default branch through Azure DevOps REST using `$env:SYSTEM_ACCESSTOKEN`, and prints the pull request address.
  - It exits non-zero with a clear message on every refusal.
  - The gallery check uses `Find-PSResource -Name Microsoft365DSC -Version <version> -Repository PSGallery` (and `Microsoft.Graph.Authentication` for the Graph pin) unless `-SkipGalleryCheck`.
- The template is a `trigger: none`, `pr: none` pipeline named `M365DSC - Bump DSC pins`, on `__POOL__`, with string parameters `version` (no default; displayName `Microsoft365DSC version to pin, for example 2.26.1104.1`) and `graphAuthenticationVersion` (default empty; displayName `Microsoft.Graph.Authentication version (leave empty to keep it)`), `checkout: self` with `persistCredentials: true` and `fetchDepth: 0`, and one script step (the parameters travel as environment variables, never spliced into the command text) running `Update-DscPin.ps1 -CreatePullRequest`.

- [ ] **Step 1: Write failing tests** in `tests/UpdateDscPin.Tests.ps1`, each on a temp copy of a pin file shaped like `Versions.psd1` (comments, two entries, CRLF and LF variants):
  - `refuses a version that is not four numbers` (`2.26`, `2.26.1104`, `v2.26.1104.1`, `2.26.1104.1; rm`);
  - `leaves the file untouched and says so when the version is already pinned`;
  - `changes only the Microsoft365DSC value and keeps comments, the other pin and the line endings`;
  - `changes the Graph pin only when asked`;
  - `the result parses with Import-PowerShellDataFile and has both keys`;

  - `accepts a version the gallery has` (mock it to return one);
  - `says it is a downgrade when the new version is lower` (message contains `DOWNGRADE`).
  In `tests/PipelineYaml.Tests.ps1` add that the new template fills with no token left and that the generated file passes its two parameters as environment variables, not inside the script text.

- [ ] **Step 2: Run them to see them fail.**

The edit is a one-line regex replacement of the value on the `Microsoft365DSC = '...'` line, so nothing else in the file moves; compare with `[version]` for the downgrade message; git and REST only under `-CreatePullRequest`, skipped when branch `dsc-pin/<version>` already exists on the remote, in which case the existing branch's pull request address is printed instead.
