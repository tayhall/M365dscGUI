# Gap analysis: where the engine stands against the full Microsoft365DSC resource list

Written 2026-10-23 after the first end-to-end Revert of a dependent chain (entitlement management) onto a second tenant.
Figures were measured on the demo blueprint (`demo`, v6) and the latest checks of the master and `contoso`, with the pinned
module 2.26.1015.1. Where something is inferred rather than measured, it says so.

## 1. Coverage today

| | Count |
| --- | --- |
| DSC resources (pinned module) | 541 |
| In the workloads we work with (AAD, Intune, EXO, Teams) | 431 |
| Resource types holding records in the blueprint | 154 (3,863 records) |
| Types deliberately excluded (mailbox- and user-level) | 24 |
| In-scope types with no records and not excluded | 253 |
| Types the master's last full check could not read (NotChecked) | 30 |

By workload (DSC resources / types in the blueprint): AAD 96 / 44, EXO 101 / 42, Intune 168 / 20, Teams 66 / 48.
Not covered at all: SC (Security and Compliance) 40, SPO 23, Azure 12, Other 11, O365 7, PP 6, Defender 3, Planner 3, M365 2,
Commerce 1, Fabric 1, OD 1 (110 resources).

The 253 empty in-scope types are mostly the demo tenant simply having nothing of them (148 are Intune), not a tooling limit:
any DSC type is compared by the same generic code. The honest reading is that **154 types are exercised, about 280 are
unproven**. "Unproven" means: its key may not be unique, it may export values that differ on every read, its own Test may never
pass after a Set, and its Revert has never been tried.

The 30 types the master check could not read fall into four groups: licence missing (Entra ID Governance lifecycle workflows),
permission missing (Global Secure Access, Windows 365 and Verified ID types: 403/401), tenant feature missing (B2C), and
**export log incomplete** (a parser/log problem in our reading of DSC's console output, not a tenant problem: federated
credentials, cross-tenant partner, group eligibility schedules).

## 2. The shape of what we built, and where it leans on DSC

DSC does the reading (export), the applying (`Start-DscConfiguration`) and the knowledge of every resource. The engine adds:
blueprints and their versions, comparison with keys, tenant-bound and noise rules, scopes, multi-tenant, decisions, the
apply guards, ordering, and the GUI/worker. The more of the 541 types we cover, the more each of these small tables has to
grow, which is the main scaling risk (section 4, class C).

## 3. Gaps, by area

### A. Resources and workloads
1. **Workloads outside AAD/Intune/EXO/Teams** (110 resources). Each needs its own authentication and permission model:
   SharePoint (the Reader would need write-capable permissions; deferred), Security and Compliance (Exchange-style connection),
   Power Platform, Defender, Azure, Planner, Fabric. None has been tried.
2. **Types that cannot be read** (30): fix the permissions we can (the Reader gets DSC's own list, so the 403s are DSC metadata
   gaps or missing admin consent to preview APIs), accept the licence ones, and fix our log parser for the "export log
   incomplete" ones, which are false NotChecked.
3. **Excluded types** (24): a deliberate scope decision (users and mailboxes). Revisit only if per-mailbox policy is wanted.

### B. Proving a type works (the biggest unknown)
4. **No round-trip test.** We have never asked, per type, "does DSC's own Test report the tenant's own export as in its desired
   state?" The access package showed why it matters: its Test can never pass for a package built from a blueprint (role-scope ids
   generated by Graph). There will be more of these. This is cheap to automate with what we have (export, build a config for each
   type from the blueprint, `Test-DscConfiguration -ReferenceConfiguration` against the same tenant) and it classifies every type as
   reliable or not before anyone relies on it.
5. **Revert exercised on a handful of types** (groups, the entitlement chain, a Conditional Access policy attempt). Apply behaviour
   per type is otherwise untested.
6. **Key quality.** Keys come from `KeyMap.psd1` and DSC's own declared keys. Duplicates show as Ambiguous (3 in `contoso`) and cannot
   be reverted. A measurement per type exists (`tools\Measure-PEKeyCoverage.ps1`) but only on the demo data.

### C. Cross-tenant portability (the replica scenario)
7. **Ids that differ per tenant.** Scanning the blueprint, 19 types hold GUID-looking values and only 6 have a tenant-bound entry.
   The rest includes Intune **assignments** (`Assignments.groupId`, six types here, expect dozens across Intune's 168), permission grant
   policy includes/excludes, authentication method targets, Teams app setup lists and role template ids. Compared across tenants
   these show as drift; applied they point at objects that do not exist. The list is hand-curated today.
8. **Identity references by name** (users, groups) must exist in the target and be resolved by DSC. We already had to resolve
   policy approvers ourselves (deviation, recorded). Conditional Access, Intune assignments and access packages all name groups
   or users.
9. **Dependency knowledge** is four small chains in `References.psd1` (entitlement management, Conditional Access to groups). DSC exposes
   none, so each chain is manual. Likely candidates: Intune policies to assignment filters and scope tags, Teams policies to app and
   user groups, Exchange rules to address lists.
10. **Tenant domain inside strings** (URLs, addresses) is only handled where DSC already tokenises it or where we listed the property.

### D. Revert / apply
11. **Write-only values.** About 44 types have secret-like property names; most are settings (password policy), a minority are
    genuinely write-only (application and service principal credentials, social identity provider `ClientSecret`, user `Password`,
    availability address space `Credentials`, Wi-Fi and VPN keys in Intune; inferred from names, not tested). Revert cannot restore what the
    export never returns.
12. **No Test after Set** (as with `Start-DscConfiguration`): a Set that silently does nothing is caught only by our drift re-check.
13. **The LCM** holds one configuration, needs an elevated session, the module and certificates machine-wide, and the PowerShell 7
    endpoint. Applies are serialised on one machine. Setup is manual today (we found five separate prerequisites).
14. **Failure handling**: the LCM carries on after a failed resource; a failed parent leaves children failing too (second pass is the
    agreed answer). There is no rollback; audit folders record what was sent.

### E. Platform and operations
15. **Data lives in a git-ignored local folder** (`data\`: blueprints, decisions, checks, scopes, tenants). Fine for one person; for a
    team or pipelines the blueprint and decisions need a shared, versioned home (the repo or a storage account) and a way to merge.
16. **Azure DevOps pipelines** (the stated direction): service principals and certificates must come from a vault or secure files, not
    the user's certificate store; the agent must be elevated for the LCM; one apply at a time per agent; module and dependency install
    for both PowerShell editions every run (slow, and it failed here until it was machine-wide). The engine functions are scriptable, but
    the scripts under `tools\` assume the user profile (`~\.m365dsc-policy`).
17. **GUI**: the worker is elevated; the web server is not. There is a startup token but no user identity or roles (anyone with the
    address and token can queue a Revert). No notification on failure. Single blueprint per worker.
18. **App registrations**: the Writer gets DSC's whole Update list (81 permissions, mostly ReadWrite), the Reader still holds nine
    ReadWrite permissions that Graph has no Read variant for. Certificates are 12 months with no rotation job.
19. **Performance**: a full export of all types takes tens of minutes and runs workloads in separate processes; scopes and per-type checks
    are the mitigation. Large types (216 service principals, 62 tabs) make findings lists long.

### F. Quality
20. **Tests are unit and mocked** (811). Live behaviour is checked by hand against two demo tenants. There is no automated live suite and
    no regression run when the DSC module version changes (the pin and guard only stop silent changes).
21. **DSC defects found so far** (each is a risk and a candidate for an upstream report):
    catalog resource exports a GUID where its siblings export names; policy approver names not resolved on create; access package Test cannot
    pass after Set; a stale `Microsoft.Graph.*` module left in the 5.1 path shadows DSC's own shim; dependency check differs between the
    editions and sessions.

## 4. Where we will have issues (ranked)

1. **Cross-tenant portability at scale (C7 to C9).** Every Intune assignment, group reference and policy-to-object link is a place a
   Revert to a replica fails or a compare shows noise. The curated lists will not keep up with 281 more types. Needs a systematic,
   data-driven approach (below).
2. **Unproven types (B4, B5).** Without the round trip, each new type is a surprise at Revert time, in front of the user.
3. **The operations model (D13, E15, E16).** The LCM route plus a local data folder works for one operator and does not translate to
   pipelines without decisions on storage, secrets, agents and serialising.
4. **Write-only values (D11).** A Revert that reports success but cannot restore a secret is a silent gap; each such type needs an
   explicit "not restorable" marking.
5. **GUI trust model (E17).** It can queue writes to production tenants with only a startup token.

## 5. Getting closer to the full list: proposed order

Each step has an exit measure so progress is visible.

1. **Round-trip classifier** (smallest, highest value). For every blueprint type: LCM Test of the type's own exported records against the
   same tenant. Output per type: reliable, Test never passes (with the differing property), error. Exit: a table for all 154 types and a
   generated list that the apply tool and the GUI use to say "this type's result is confirmed by the re-check only".
2. **Portability report.** Turn the id/identity scan into a command (per type: properties holding ids or names of other objects, which
   are already handled, which are not). Decide one policy per class: ignore across tenants (assignments), resolve by name (users), or
   mark "not portable". Exit: no unclassified GUID-valued property in the blueprint.
3. **Widen the blueprint** by workload in batches (Add-PEBlueprintType), starting with the 253 empty in-scope types that a richer test
   tenant can populate, run each batch through steps 1 and 2. Fix the three false NotChecked parser cases and the permission 403s.
4. **Decide the first new workload** (suggest Security and Compliance, then Defender; SharePoint needs the permission decision) and
   work out auth and Reader permissions on one resource before adding the rest.
5. **Operations**: shared home for blueprints, decisions and checks; an ADO pipeline definition for check and Revert (certificates from a
   vault, elevated agent, one apply per agent); app certificate rotation; scripted machine setup for the LCM prerequisites; GUI roles.
6. **Live test suite and upgrade procedure**: the round-trip run plus a small set of create/revert/remove cycles against a scratch
   tenant, run on every module version bump and before every release.

## 6. Decisions needed from the project owner

- Is the aim full parity with all 541 resources, or the tenant-policy resources in the four workloads plus a chosen few more?
- Which workload is next (Security and Compliance, Defender, Power Platform, SharePoint)?
- Where do blueprints and decisions live for a team and pipelines (repo, storage account)?
- Is a richer scratch tenant available to populate the empty types, and may the Writer be used there freely?
- Intune assignments: ignore across tenants, resolve groups by name, or mark not portable?

## 7. Progress: round-trip classifier (step 1)

`Invoke-PERoundTrip` (`tools\Invoke-PERoundTrip.ps1`) takes up to N records of every blueprint type, builds the configuration a Revert would send, and
asks the LCM to Test it against the tenant the blueprint came from (Reader app, nothing changed; elevated session). Each type becomes Reliable,
NeverMatches, Mixed, RenderFailed or TestError; results go to `data\roundtrip\latest.json`. `-RenderOnly` stops before the LCM and needs no
elevation.

**First result, render only, demo blueprint v6 (2026-10-23): 138 of 154 types build, 16 do not**, so a Revert of those types is impossible today:

- **15 types: "the Key property 'Id' is missing from the record".** `Id` is on the global ignore list (it is normally a tenant-generated GUID) and
  is removed from every record, but for these types DSC's own key is `Id`: the ten `AADAuthenticationMethodPolicy*` types (readable ids such as
  `MicrosoftAuthenticator`), `AADDomain`, `AADPermissionGrantPolicy`, `AADRoleManagementPolicyRule`, `IntuneDeviceEnrollmentPlatformRestriction`,
  `IntuneDeviceManagementEnrollmentAndroidGooglePlay`. Compare works (the key is built before `Id` is dropped); only the renderer cannot supply it.
  Needs a rule: where DSC's key is `Id` and the value is not a tenant-specific GUID, keep it or rebuild it from the record's key.
- **1 type: `IntuneCustomizationBrandingProfile`**, whose exported default profile has no `DisplayName` (DSC itself warns the export misses a mandatory
  property). A DSC export defect.

Next: run it with the LCM (elevated) to classify the 138 that build.

## 8. Progress: Security and Compliance (the one new workload, 2026-10-23)

**Sign-in.** The existing Reader app (Global Reader plus `Exchange.ManageAsApp`, which the Exchange types already needed) connects with
`Connect-IPPSSession` and a certificate. No change to the Reader was needed to read most of it. The extra steps DSC's documentation lists
(register the app in Security and Compliance, eDiscovery Manager, case admin, Compliance Administrator role) were deliberately **not** done,
because they make the Reader write-capable there.

**Result of exporting all 40 resources with that Reader** (13 minutes, 605 instances):

| | Types |
| --- | --- |
| Read, with data (added to blueprint `demo` v7, 17 types, 600 records) | SCComplianceTag, SCDLPCompliancePolicy, SCDLPComplianceRule, SCDLPSensitiveInformationType, SCFilePlanPropertyAuthority/Category/Citation/Department, SCInsiderRiskEntityList, SCLabelPolicy, SCPolicyConfig, SCProtectionAlert, SCRetentionCompliancePolicy, SCRetentionEventType, SCRoleGroup, SCRoleGroupMember, SCSensitivityLabel |
| Read, empty (12) | SCAdaptiveScope, SCAppRetentionCompliancePolicy/Rule, SCAutoSensitivityLabelPolicy/Rule, SCDeviceConditionalAccessPolicy/Rule, SCDeviceConfigurationPolicy/Rule, SCDLPSensitiveInformationTypeRulePackage, SCFilePlanPropertyReferenceId/SubCategory |
| Failed: the cmdlet does not exist in the Reader's session (10) | SCAuditConfigurationPolicy, SCCaseHoldPolicy/Rule, SCComplianceCase, SCComplianceSearch, SCComplianceSearchAction, SCInsiderRiskPolicy, SCRecordReviewNotificationTemplateConfig, SCSecurityFilter, SCUnifiedAuditLogRetentionPolicy |
| No records, log reported incomplete (1) | SCRetentionComplianceRule |

The 10 failures are role-gated cmdlets (`Get-ComplianceCase`, `Get-InsiderRiskPolicy`, `Get-AuditConfigurationPolicy`, ... are absent from the app's
25,799 visible commands) and show as NotChecked. **Silent empties are the real risk**: the master has 6 retention policies but
`Get-RetentionComplianceRule` returns no rule for any of them, which suggests the rules are hidden by a missing role and not absent. The 12
"empty" types may be hidden the same way (inferred, not proven). A blueprint of a hidden type records nothing and can never show drift.

**Stability.** A full check of the 17 types against the master itself returns no Missing or Changed finding, so none of them exports volatile
values. The only findings are 2 Ambiguous sensitivity labels.

**Known gaps found**
- **Sensitivity label keys are not unique**: sub-labels share a display name under different parents ("All Employees", "Anyone (unrestricted)"), so
  4 of 14 labels are Ambiguous and were not added. A key of parent plus name is needed, and the parent is exported as a tenant-generated id, so it
  has to be turned into the parent's name the way `ResolveGuid` does for the catalog (that mechanism looks the parent up by `Id`; labels use `Name`).
- `SCSensitivityLabel.Name` is a tenant-generated id (a GUID for built-in labels), so it must be tenant-bound for the replica scenario.
- The round trip (LCM Test) for the SC types is not run yet, and the replica (`contoso`) has not been checked for SC.
- `SCRoleGroup` and `SCRoleGroupMember` are privilege-bearing and kept visible (not excluded), 82 records each, mostly built-in.

## 9. Progress: keys and rendering fixes (2026-10-23/24)

**Key audit against DSC's declared keys** (blueprint v7, 124 types whose schema declares a `[Key]`): our key equals DSC's for 103, differs for 21.
Where it differs the blueprint's own values were unique except for sensitivity labels, but the audit shows where a second tenant could collide
(for example `AADGroup`: DSC's key is DisplayName plus MailNickname, ours DisplayName; `AADServicePrincipal`: DSC's is AppId, ours DisplayName).

**Done for Security and Compliance:** DSC declares `Name` as the key of `SCDLPCompliancePolicy`, `SCDLPComplianceRule`, `SCInsiderRiskEntityList`,
`SCRoleGroup` and `SCSensitivityLabel` (its label resource also refers to a parent by that `Name`). `KeyMap.psd1` now uses it for those five.
`Update-PEBlueprintKeys` (restored, it is the migration for exactly this) re-keyed 89 records (blueprint v8) and the 4 labels that had been ambiguous
were added (v9). A full check of the 17 SC types against the master now shows no Ambiguous finding. Caveats: `Name` is a tenant-generated id for
portal-created labels (8 of 14, including Microsoft's defaults), so those labels do not match across tenants; and three role groups
(`DSPMAdmins`, `DSPMAnalysts`, `DSPMInvestigators`) appear in some exports and not others, which shows as intermittent TargetOnly.

**Done in the renderer (the round-trip render-only pass found these):**
- A `[Key]` that the global ignore list removes from every record (`Id`) is rebuilt from the record's own Key when the key map builds the Key from
  that property (single or one part of a composite key): `Get-PEKeyPartFromRecordKey`. The generated-config safety check allows that name for those types.
  Fixes the ten `AADAuthenticationMethodPolicy*` types, `AADDomain`, `AADRoleManagementPolicyRule` and `IntuneDeviceManagementEnrollmentAndroidGooglePlay`.
- The per-value size limit rose from 32,768 to 131,072 characters: a real DLP rule's `AdvancedRule` is 37 KB.

**Still not renderable (3 of 171 types):** `AADPermissionGrantPolicy` and `IntuneDeviceEnrollmentPlatformRestriction` (their `Id` is not in the blueprint and no
key map entry builds the Key from it; the id would have to be kept, a policy decision for ids that are stable readable names versus tenant GUIDs) and
`IntuneCustomizationBrandingProfile` (DSC's own export omits the mandatory `DisplayName` of the default profile).

## 10. Progress: ids across tenants (2026-10-24)

The blueprint GUID scan (19 types hold GUIDs) turned out to need almost no lookups: the group ids in Intune assignments are covered by DSC's own
`groupDisplayName` fallback, the Teams ids sit beside names, and the rest are stable global ids. What did need the id was the object's own `Id` where it
is DSC's key (`AADPermissionGrantPolicy`, `IntuneDeviceEnrollmentPlatformRestriction`): kept in the record and looked up in the target with DSC's export
at Revert time (blueprint v10). Round-trip render-only pass: 170 of 171 types build; the remaining one is a DSC export defect.

**NeverMatches (5), diagnosed in-process:**
- `AADPasswordRuleSettings`, `AADGroupsSettings`, `AADOrganizationCertificateBasedAuthConfiguration`, `EXOReportSubmissionPolicy`: DSC's `Get` reads the object
  back as `Ensure = Absent` while its export listed it as Present with values (a setting never created; the export shows defaults, `Get` says it does not
  exist). A Revert would create it and the Test would then pass. No property differs by value.
- `EXOGroupSettings`: two groups share the display name "All Company", `Get` returns the Viva Engage one (different address and notes), so the Test compares the
  wrong group. A key problem (display name is not unique), not a settings difference.

**TestError (18):** `EXOHostedOutboundSpamFilterPolicy`: DSC's Test calls a cmdlet with `-Identity` that does not accept it (a DSC defect in that resource).
The 17 Security and Compliance types all fail the same way through the LCM ("Object reference not set to an instance of an object.") although the same
resource passes `Test` in-process with the same app and certificate (`SCComplianceTag`: InDesiredState). Exchange types use the same sign-in module and pass in
the LCM, so the cause is specific to how Security and Compliance connects inside the LCM's PowerShell.7 session. A Revert of Security and Compliance types
through the LCM is therefore blocked until that is understood. Not diagnosed yet (needs an elevated probe of that session).

**RenderFailed (1):** `IntuneCustomizationBrandingProfile`, DSC's export omits the mandatory `DisplayName` of the default profile.

## 12. Security and Compliance through the LCM: investigation (2026-10-24)

All 17 readable Security and Compliance types fail a Test through the LCM with "Object reference not set to an instance of an object." Findings:
- DSC's own event log (`M365DSC`) holds the stack: thrown inside the Exchange Online module's .NET connection code and rethrown at `Connect-ExchangeOnline`
  (`ExchangeOnlineManagement` 3.9.2, `netCore\ExchangeOnlineManagement.psm1` line 595), reached from `Connect-IPPSSession` (line 787) through
  `MSCloudLoginAssistant` 1.2.9 (`Workloads\SecurityCompliance.ps1` line 70, `ConnectionProfile.ps1` line 926) and `New-M365DSCConnection`.
- The same connection works as SYSTEM in a plain process, as SYSTEM inside the real `PowerShell.7` endpoint opened exactly as DSC opens it
  (`New-PSSession -ComputerName localhost -ConfigurationName PowerShell.7 -EnableNetworkAccess`; host `ServerRemoteHost`; 6 retention policies visible),
  in-process through DSC (`SCComplianceTag`: InDesiredState), and with empty or null connection address and search-only values.
- So identity, certificate, host, session and the connection settings are not the cause; it is specific to a resource call relayed by the LCM. Not isolated.
- Effect: Security and Compliance can be exported, checked and compared but not reverted through the LCM. Options recorded: report upstream and keep it
  check-only (preferred), apply those types in-process with `Invoke-DscResource` (a deviation, needs agreement), or trace the LCM call further.
