## Conventions

- PowerShell 7.6+, LF line endings (`.gitattributes`), no C#. Function bodies use Allman braces, 4-space indent. Pester blocks keep the opening brace on the same line.
- Public commands live in `src/PolicyEngine/Public/*.ps1` and every top-level function there is exported. Everything in `Private/` is tested with `InModuleScope PolicyEngine`.
- Import Microsoft365DSC with an explicit version. The versions are pinned in `src/PolicyEngine/Data/Versions.psd1`.
- Secrets, certificates, exports and tenant data never go in the repo. `~\.m365dsc-policy\` holds the Reader and Writer app JSON files; the private keys are in `Cert:\CurrentUser\My`. `data\` is git-ignored.
- Checks, scans and delta exports use the Reader app only. The Writer app is for apply only.

## Decisions that differ from or extend the plan

- **Keys.** `KeyMap.psd1` has overrides, composite keys (parts joined with ` | `, separators escaped inside a part) and a `Singletons` list. No record is unkeyed on the test tenant.
- **Comparison.** Pure PowerShell. Strings compare case-sensitively; keys match case-insensitively; arrays compare as sets (so two elements differing only in an ignored nested member read equal).
- **Finding kinds:** Missing, Changed, TargetOnly, Ambiguous, PossibleRename, NotChecked, NotAvailable, Unkeyed, Unreadable, Excluded.
- **Possible renames are conservative.** Any Missing or TargetOnly item with a similar counterpart becomes `PossibleRename` with a hint naming all candidates. These are never offered for Remove or Create unless the user passes `-ConfirmNotRenamed`. Above 20,000 candidate pairs for one type, the check is skipped and the finding keeps its Kind with a hint; Remove refuses any finding that carries a hint. A quick scan applies the same rule, so while any group is missing, every group finding in that scan is a PossibleRename (a delta export still covers the target-side ones).
- **Excluded types** (`Data/ExcludedTypes.psd1`): user and mailbox-bound types (design: users out of scope), and the built-in role entries of Exchange; entries of custom roles stay compared. Admin-role types are compared on purpose (a new admin must stay visible); the reasons are in `docs/key-coverage.md`. `Compare-PEState -IncludeTypes` overrides the exclusion for one call.
- **Nested ignores** (`Data/IgnoredProperties.psd1`): dotted paths such as `ScheduleInfo.startDateTime`, applied only when the value is at or before the record's export time (DSC does the same). Arrays keep their length.
- **Unmanaged** applies to TargetOnly findings only. **Decisions** are stored in `decisions.json`; `Get-PEDecision` returns normal output, so callers wrap it in `@()`.
- **Blueprints** are immutable versions with a change record each, written crash-safely under a per-blueprint lock. Accepting a blueprint change takes records from the fresh master state only.
- **Export log.** `Invoke-PELoggedCommand` flattens control characters; the parser (`Private/ExportLog.ps1`) gives each exported type Ok, Failed or Incomplete. Failed and Incomplete become NotChecked, never Missing. Several types stay Incomplete on purpose (they print nothing on zero objects, or DSC prints their mark too early); see the D1 section of `docs/acceptance-v1.md`.
- **Apply.** `Invoke-PERectify` generates the config (ASCII only, no executable text from tenant data), saves the audit folder, then applies through a child process (`tools/Invoke-PEApply.ps1`, `Invoke-DscResource` in PowerShell 7, no LCM, not elevated). Preconditions: the plan must come from the latest blueprint version and from a check whose tenant equals the Writer app's tenant; `-ConfirmMasterWrite` is required for Target Master or any Promote; Promote needs `-Reason`; plans are single-use. Plan, config and apply must run in one PowerShell session.
- **Status.** Records of NotChecked and Excluded types never count as aligned.

## Scopes and scheduled scope checks

A **scope** is a named slice of the tenant that is checked on its own: resource types (exact DSC names) and, optionally, wildcard patterns on the item key (`scopes.json` in the data root; `Get-PEScope`, `Set-PEScope`, `Remove-PEScope`). `Invoke-PEScopeCheck -Scope <name> -BlueprintName <b>` exports only those types (one Reader-app export), classifies them from `export.log` like a full check, compares the scope's slice of the blueprint with the export, and folds the result into the latest Full check as a new Full-kind check (`Meta.PatchedFrom`, `Meta.ScopeChecks`, `Meta.ExportedAt` unchanged), so the GUI and rectify keep reading one consistent state. A Full check must exist first. Timing on the dummy tenant: CA policies 20 s, groups matching `sg-*` 20 s (29 groups), against about half an hour for everything.

- **Every DSC resource is a scope of its own.** Get-PEScope -Name AADGroup, Invoke-PEScopeCheck -Scope AADConditionalAccessPolicy and Register-PEScopeSchedule -Scope AADGroup work without defining anything: the resource names come from the pinned module's ResourcePermissions.json (541 in 2.26.1015.1), so new resources appear when the pin moves. A defined scope of the same name wins (for example AADGroup limited to sg-*). A scope whose types the blueprint holds no item of is refused (every object would read as Target-only) unless -AllowTypesNotInBlueprint. The GUI lists each resource type of the blueprint under **Check by resource type**, grouped by workload, with items, drift, last check and a **Check now** button.
- Key patterns narrow what is judged, not what is read: the whole type is exported and compared, so a rename whose new name falls outside the pattern is still paired with its missing original; findings about unrelated items outside the pattern are dropped.
- Schedule: `tools/Register-PEScopeSchedule.ps1 -BlueprintName <b> -Scope <s> (-EveryMinutes n | -DailyAt hh:mm) [-Unregister]` creates the task `PE-Scope-<b>-<s>` (same rules as the other tasks: current user, interactive logon, one instance, one hour limit). `tools/Invoke-PEScopeCheck.ps1` is what it runs.
- GUI: the Overview lists the scopes (items, drift, last checked) with a **Check now** button each; the worker runs a Recheck request with a `scope` through `Invoke-PEScopeCheck`. The plain **Re-check now** still checks every type in the blueprint.
- Not done: narrowing the export itself by key (DSC supports filters, but the blueprint would need the same filter, so v1 reads the whole type), a GUI editor for scopes (use `Set-PEScope`), schedule shown in the GUI, per-scope blueprints.
## Several tenants (master and replicas)

One blueprint, taken from the **master**, is compared with any number of **replicas** (for example a Dev tenant), and a replica can be brought into line with it. Built unattended on 2026-10-23; **nothing has been run against a second real tenant yet** (the tests use fixtures and mocks).

- **Registry.** `tenants.json` in the data root (`Get-PETenant`, `Set-PETenant`, `Remove-PETenant`). The slug `master` is the Master; every other slug is a Replica. With no file the master comes from the Reader app file, so older installations keep working.
- **App files.** `tools\PEAppPath.ps1` is the one rule (dot-sourced by the module and the tools): master keeps `~\.m365dsc-policy\M365DSC-Policy-<Role>.json`, a replica has `~\.m365dsc-policy\<slug>\M365DSC-Policy-<Role>.json`.
- **`-Tenant` (default `master`)** on `Invoke-PEFullCheck`, `Invoke-PEScopeCheck`, `Export-PEDelta`, `Invoke-PERectify`, `Get-PECheck`, `Add-PEBlueprintType` (refused for a replica: the blueprint comes from the master) and `tools\Export-M365DscTenant.ps1`. Check documents carry `TenantSlug`; one written before tenants belongs to the master. A scope check folds into the latest Full check of that tenant only. Unmanaged and Remove decisions can be for one tenant (`-Tenant`), noise rules stay global. Reverting a replica uses its own Writer app and `-Target Replica` (no master-write confirmation); reverting the master still needs it.
- **GUI.** `Export-PEGuiData` writes one entry per registered tenant (a tenant with no check yet is listed empty and reads "not checked"); the Overview has a tenant picker for the scope cards and the Re-check button; Drift review, Revert, Exclude work per tenant row. A replica's **Promote is not offered** by the worker (it would write to the master); only the master can promote into the blueprint.
- **Same blueprint, different tenant, so expect noise.** Object ids, domains and referenced users and groups differ between tenants. We compare as is and tune with ignore rules as they show up (decision made); the Intune assignment `groupId` proposal in `docs\acceptance-v1.md` is the first candidate.
- **GUI security first.** Because the GUI can now register tenants it needs the startup token, host and origin checks (`Test-PEGuiRequestAllowed`, see `gui\README.md`).

### Connecting a tenant, and what DSC's own app command can and cannot do

Decision: lean on DSC. `Get-PETenantSetupScript` (and `tools\Get-PETenantSetup.ps1`, and the Tenants page of the GUI) gives an administrator of the new tenant the DSC commands to run: DSC's own permission lists (`Get-M365DSCCompiledPermissionList`, DSC's list for the manual route; the automatic route narrows the Reader's ReadWrite entries to Read where Graph has one) and `Update-M365DSCAzureAdApplication` for the app, its permissions and a self-signed certificate. `Connect-PETenant` (`tools\Connect-PETenant.ps1`, the Tenants page) then records the application ids and thumbprints, proves the Reader can sign in and registers the replica. This is the manual route you asked to keep.

Limits found in `Update-M365DSCAzureAdApplication` (2.26.1015.1), which is why the automatic route is our own code (decision: use DSC where it makes sense, build where it does not):
1. It signs in with a username and password, an existing app or a managed identity. No interactive, device-code or MFA sign-in, so it cannot start on a tenant that has no app.
2. Admin consent only works with `-Credential` (it calls an internal Azure portal endpoint), not with app authentication.
3. It does not create the service principal and does not assign directory roles (Global Reader, and so on); it prints a note to do that by hand.
4. It returns nothing (host output only), and its API-name lookup (`Get-M365DSCApiServicePrincipal`) is internal to a nested module, so it cannot be called.

**The automatic route** is `tools\New-PETenantApps.ps1` (it replaces `New-M365DscAppRegistration.ps1` and `Set-M365DscAppRoles.ps1`, which are gone) and the **Connect a tenant > Create the apps for me** tab of the GUI. From DSC it takes the resource list (`Get-M365DSCAllResources`) and the permission lists (`Get-M365DSCCompiledPermissionList`, exactly as given, no narrowing). The administrator signs in with a device code (MFA works) and, with that token, the script creates the app and certificate, the service principal, the admin consent and the directory roles, then `Connect-PETenant` proves the Reader can sign in and registers the tenant. Reader gets Global Reader; the Writer gets no directory role unless the form asks for Exchange Administrator and Teams Administrator (narrower than the Global Administrator the old script used). The worker runs it in a child process and shows the sign-in code in the job (Activity and the Tenants page) while it waits; a 20 minute limit applies. It needs an administrator who can consent. **Found on the first real try:** the Graph PowerShell SDK's own device sign-in (`Connect-MgGraph -UseDeviceAuthentication`, SDK 2.41) printed a second code after the administrator had signed in with the first and gave up after 120 seconds, and Microsoft's current device address is `https://login.microsoft.com/device` (not `.../devicelogin`). The device flow is therefore ours (`tools\PEDeviceLogin.ps1`, about 30 lines against Microsoft's `devicecode` and `token` endpoints, client `14d82eec-...` = Microsoft Graph Command Line Tools, 15 minutes to use the code) and `Connect-MgGraph -AccessToken` is given the token; the sign-in is also done first so the code appears within seconds. The sign-in was verified live against a second tenant (token for the right tenant and administrator with the four scopes needed); the app creation itself has not been run there yet. Test by running `pwsh -NoProfile -File tools\New-PETenantApps.ps1 -Slug <name> -TenantId <domain>` or from the GUI, then a check for that tenant.

**Safety of the automatic route (from two security reviews).** Only an application this tool recorded creating is ever reused: its object id is written to `~\.m365dsc-policy\created-apps-<slug>.json` the moment it is created, and an application that merely has the same name is refused (anyone who can register an application could have pre-created it and would otherwise receive consent and directory roles). Neither a certificate identifier (the caller who adds a key picks it) nor the name is trusted. A recorded application is also refused if it has gained a client secret, has other than exactly one key, has a federated credential or has an owner other than the signing-in administrator (`Test-PEAppOwnership`); an existing service principal of a reused application is refused if it has credentials or foreign owners (`Test-PEServicePrincipalOwnership`). The Reader gets DSC's read list, narrowed by `Convert-PEPermissionToRead` (reversal of the earlier "exactly DSC's list" decision, after seeing 56 of 81 were ReadWrite because DSC's own per-resource Read lists name them): ReadWrite becomes Read where Graph offers a Read permission (47 of 56); the other nine (Application.ReadWrite.OwnedBy, several Policy.ReadWrite.*, two Verifiable Credentials) stay, and the script and job result list them. The Writer keeps DSC's update list as is.

The manual route stays: `Get-PETenantSetupScript` and the **I already created them** tab, then `Connect-PETenant`.
SharePoint is deliberately not in the app permissions (DSC lists the same write-capable set for reading it; decided to skip).
## Growing a blueprint, and the first scale test (Entra governance)

`Add-PEBlueprintType -Name <b> -Types <types> -Reason <text> [-AllowExistingTypes] [-WhatIf]` adds every item of the given resource types, as the tenant has them now, to the blueprint as a new version (export of just those types, export.log classification, then `Approve-PEBlueprintChange` for the new items only; other types are never touched; Ambiguous items are counted and skipped; types that failed to export are reported). It makes the current state the approved state, so review before adding roles, PIM settings or entitlement packages.

Scale test on the dummy tenant, blueprint `demo` v1 (34 items) to v2: 15 resource types (Entra entitlement management, PIM, roles), **2,776 items** from 12 types that exported (`AADRoleManagementPolicyRule` 2,465, `AADRoleDefinition` 145, `AADRoleSetting` 145, `AADRoleAssignmentScheduleRequest` 13, access packages, catalogs, assignment policy, settings). Export of the 15 types 58 s; whole add 160 s (about 100 s of that is writing the version); a scope check of the same 15 types 80 s; GUI export 14 s (2,847 files, 6 MB; `items.json` 840 KB). In the browser: Overview 1.2 s, Blueprint 1.5 s, version 2 with all 2,777 change rows 1.5 s. About 10,000 items or more would need paging (items list, version change list). Not added: `AADGroupEligibilitySchedule` (export log incomplete), `AADGroupEligibilityScheduleSettings` and `AADPIMGroupSetting` (not in the export log); entitlement `ConnectedOrganization`, `RoleAssignment` and `RoleEligibilityScheduleRequest` exported but are empty in this tenant. Scope `entra-governance` covers all 15.

**Finding: Graph returned different data for the same objects within minutes.** One of three consecutive scope checks reported 3 `AADRoleDefinition` items as Changed: Conditional Access Administrator, Global Administrator and Security Administrator each lacked the three `microsoft.directory/conditionalAccessPolicyPlans/*` permissions in that export only; the exports before and after had them, and the third check showed no drift. This is server-side flapping (the export had no error), not a comparison bug, and on a real tenant with thousands of governance items it will happen again. Direct Graph calls confirmed it: six reads of Global Administrator through v1.0 and six through beta each alternated between 262 and 265 permissions. **Rule added:** Data\BuiltInResources.psd1 lists the 145 built-in Entra role ids with their names (Microsoft's directoryRoleTemplates, identical in every tenant; Global Administrator is 62e90394-69f5-4237-9190-012177145e10) and Compare-PEState does not compare RolePermissions for a role whose TemplateId AND exact DisplayName both match the list, on both sides. The id alone is not trusted (a security review pointed out that a custom role can be created with any templateId, which would hide its permissions); a custom role under another name is compared in full. Not done: a GUI warning when permissions are skipped. Custom roles (any id not listed), role settings, PIM rules and assignments stay fully compared, and a built-in role that goes missing or appears still shows. 	ools\Update-PEBuiltInRoles.ps1 refreshes the ids from Graph (Reader app). Another mitigation, not built: confirm-before-report, where a scope check re-reads only the types that show Changed findings and keeps the findings that both reads agree on.
**Rest of Entra and Intune (blueprint `demo` v3).** One `Add-PEBlueprintType` call over the 250 remaining `AAD*` and `Intune*` types (not the per-user `AADUser` and `AADAuthenticationRequirement`): export plus approval 190 s; 52 types had items, 308 items in all (`AADServicePrincipal` 211, `AADPermissionGrantPolicy` 14, `IntuneRoleDefinition` 10, `IntuneAppCategory` 9, `IntuneMobileAppsStoreApp` 8, `AADApplication` 7, `AADNamedLocationPolicy` 4, the rest 1 to 3 each); no ambiguous keys. 30 types did not export and were reported, not added: 403 or access denied (14), insufficient licence (3), B2C or self-service sign-up not enabled (3), 401 (2), export log incomplete or the type missing from the log (8). A full check of the grown blueprint (Entra and Intune workloads, 64 types in the GUI) took 228 s and found no drift other than the `sg-Executive` rename; GUI export 12 s (3,221 files). This tenant is small in Intune and has no custom roles, so noise from busier tenants is still untested.
**Exchange, Teams and SharePoint (blueprint `demo` v4 and v5).** Added per workload in separate processes, because one export that went from the SharePoint types (all failing) on to Teams crashed with a stack overflow inside PnP.PowerShell's assembly resolver (exit code -1073741571), taking the whole export with it; nothing had been written. `EXO*`: 42 types, 565 items in 192 s (`EXODataClassification` 225, `EXOManagementRoleAssignment` 212, `EXORoleGroup` 31, ...), 12 types not exported (cmdlets missing in the tenant, incomplete logs, one server error). `Teams*`: 48 types, 180 items in 158 s, 1 type incomplete. `SPO*`: none of 23 types exported (the Reader app is Unauthorized in SharePoint; needs a SharePoint application permission, not done). Types in `ExcludedTypes.psd1` (per-mailbox and per-user types, `EXOManagementRoleEntry`) were not added. A check of all 154 blueprint types as one scope (`whole-blueprint`) took 434 s for 3,863 items; GUI export 23 s, 3,966 files, 9 MB.

**Intune built-in roles.** That check showed 4 `IntuneRoleDefinition` items Changed: built-in roles had gained permissions (`Microsoft.Intune_ShieldingExclusions_*`, `Microsoft.Intune_Recovery_*`) since the blueprint was read, the same class as the Entra roles. `BuiltInResources.psd1` now also covers `IntuneRoleDefinition`: for a role flagged `IsBuiltIn = True` whose exact name is one of Microsoft's 10 built-in roles, `AllowedResourceActions` and `NotAllowedResourceActions` are not compared (custom roles, and a custom role that borrows a built-in name, are compared in full). `tools\Update-PEBuiltInRoles.ps1` now refreshes both the Entra and Intune lists from Graph.
## When the Microsoft365DSC pin changes

- **Guard.** Each blueprint records the Microsoft365DSC version it was built with (`blueprints\<name>\module.json`, written by `Initialize-PEBlueprint`; `Set-PEBlueprintModule` re-stamps it). `Invoke-PEFullCheck`, `Invoke-PEScopeCheck`, `Add-PEBlueprintType` and `Invoke-PERectify` refuse to run when the pin in `Data\Versions.psd1` differs, with the message saying how to re-baseline; the checks and `Add-PEBlueprintType` accept `-AcceptModuleChange` (a warning instead), rectify never does. `Get-PEModuleStatus -BlueprintName <b>` shows pin, recorded version and match. A blueprint with no recorded version (made before the guard) only warns; `demo` and `test` were stamped on 2026-10-23. Full checks also store `Meta.ModuleVersion`. The Overview shows a red banner when the versions differ (`index.json` has `dsc: { pin, blueprint, match }`); the GUI offers no bypass.
- **Re-baseline after moving the pin:** run a check with `-AcceptModuleChange` (the effect of the upgrade shows as drift: renamed or removed properties, changed defaults), review it, Promote what is expected (blueprint-only), then `Set-PEBlueprintModule -Name <b> -Reason '...'`.

### Moving to 2.26.1021.1 and what the GUI does about a pin change (2026-10-27)

- **Pin moved** from 2.26.1015.1 to 2.26.1021.1 (`Data\Versions.psd1`; tests and fixtures follow the pin). The LCM runs as SYSTEM and only sees `C:\Program Files\WindowsPowerShell\Modules`, so the module must be copied there as well as installed for pwsh (`tools\Install-M365DscDependencies.ps1` installs for the current user only). Until then every type of a round trip fails with "resource does not exist at the PowerShell module path".

- **GUI refresh no longer stops at the guard.** A Recheck passes `-AcceptModuleChange`. The Overview/Drift banner lists the steps (review the drift, mark reviewed), counts the items whose tenant has a setting the blueprint lacks, and links DSC's changelog (not copied). "Mark reviewed" is the request `ReviewModule`: it runs `Set-PEBlueprintModule` for every blueprint built with another version. Reverts stay refused until then.
- **Round trip not re-run on 1021.1** (it needs the module under Program Files and takes about 25 minutes). The 1015.1 results in `data\roundtrip\latest.json` were overwritten by the failed run; `data\roundtrip\20261024-082308.json` is the last valid one.

### Snapshots, baselines and restore (2026-10-27)

- **Words:** snapshot (a stored reading, `Kind = 'Full'`), refresh (partial re-read, `PatchedFrom`), compare (snapshot against a blueprint). See `docs\overview.md`, "Words used in the GUI".
- **After a Promote** only the promoted items are compared with the new blueprint version again, with no tenant read (`Update-PECheckForItems`, a new check with `Meta.PatchedFrom`).
- **`New-PETenantBaseline`** (checkbox "use as blueprint" on New snapshot of a replica): the replica's own blueprint gets a new version matching its latest snapshot, built from `Get-PEBlueprintChange` and `Approve-PEBlueprintChange`. A baseline snapshot reads every default workload, not only the blueprint's types, so types new in DSC are included. Left out: items marked Unmanaged for the tenant, renames and duplicate keys (need a decision), types the snapshot could not read. The master tenant has no checkbox.
- **`Restore-PEBlueprintVersion`** (the Restore buttons on the master blueprint's versions): a new version that is a copy of an older one, or of one item of it; history is kept (`changes\vNNNN.json` has `RestoredFrom`). Tenant blueprints have a page (tabs, versions, compare) but no Restore button yet: the request does not name a blueprint.
- **Not done:** the engine command names still say check (`Invoke-PEFullCheck`, `Invoke-PEScopeCheck`); only the GUI words changed.
- **New resources.** A resource added by the new module is a scope and can be added with `Add-PEBlueprintType` straight away. Its key now comes from the DSC schema: when there is no override in `KeyMap.psd1` and none of DisplayName, Name or Identity is present, the key is the resource's own `[Key]` properties (sorted, joined with ` | `; never `Id`, which is the tenant's GUID and is stripped). Types that already have a key keep it. Of the 541 resources in 2.26.1015.1: 348 have a DisplayName, Name or Identity key, 79 are singletons, 35 have an override, and 79 declare other or composite keys (for example `AADGroup` declares DisplayName + MailNickname, and we key on DisplayName alone, so duplicate names read as Ambiguous). Still manual: noise rules for new volatile properties, and Revert for Id-keyed types.

## Same-tenant and cross-tenant comparison (tenant-bound properties)

A blueprint remembers the tenant it was taken from (`Meta.TenantId`). `Compare-PEState` treats a target as **cross-tenant** when its `Meta.TenantId` is known and differs from the blueprint's (`-CrossTenant Auto|Yes|No`, `Test-PECrossTenant`). Against the tenant the blueprint came from everything is compared, so a deleted and recreated app, a changed domain or a new key shows as drift. Against another tenant (a dev tenant checked against the production blueprint) the `TenantBound` section of `Data\IgnoredProperties.psd1` is left out of each matched pair: ids generated per tenant (service principal `ObjectID`, application `AppId`/`ObjectId`/scope ids, team and group ids, mailbox plan identities, retention ids) and values naming the tenant's own objects (tab configuration, group addresses, distribution group OU). Those entries are not removed from stored states or blueprints, and the Revert plan for a different tenant strips them from the blueprint record so the source tenant's ids are never rendered into the target. Anything that grants or changes access (role group members, application credentials, pre-authorised applications, Intune assignments) is deliberately not tenant-bound. Check documents carry `BlueprintTenantId` and `CrossTenant`; the GUI shows the blueprint's source tenant and, per tenant, which mode applied. Not done: a generic substitution of the tenant's own domain inside strings (for example `*.sharepoint.com` URLs); only the properties listed are handled, and objects that exist in one tenant only (Missing/TargetOnly) remain per-object decisions.

## Revert of dependent items (entitlement management and similar)

- **Selection.** The Drift and type pages keep their ticked rows while you move between pages; **Revert selected** opens one dialog and one job for everything ticked (for each tenant). The selection is cleared when a job is submitted.
- **Order.** DSC's own export is alphabetical with no `DependsOn` (access packages before catalogs), and the apply tool refuses `DependsOn`, so the order of the blocks is the only ordering there is. `Data\References.psd1` says which property points at which parent type; a Revert puts Create first, then Update, then Remove; within Create/Update parents first (depth in that graph), within Remove children first. The apply tool runs in that order and stops at the first failure (the rest are "Not run"; the job result lists what was applied and what failed).
- **A parent that is not picked** (a package whose catalog is missing too) is not added for you. If the apply fails on it, re-check and Revert again: DSC reports what exists as already correct and creates the rest.
- **No Test after Set.** The apply tool Tests each resource, Sets it when needed and reports Applied if the Set did not throw. It does not Test again, as `Start-DscConfiguration` does not: an access package can never pass its own Test after a Set (DSC compares the role-scope pair ids Graph generates), and the engine's drift re-check of the tenant is what confirms the result.
- **Keys.** `AADEntitlementManagementAccessPackageAssignmentPolicy` is keyed `<access package> | <name>` (every package has an "Initial Policy"), `KeyMap.psd1`; the demo blueprint was re-keyed (v6).
- **Names, not ids.** DSC resolves display names for the catalog (`CatalogId`) of a package and catalog resource and for `AccessPackageId` of a policy, so the blueprint works in another tenant. One gap in DSC: its *export* writes the catalog's **GUID** into `AADEntitlementManagementAccessPackageCatalogResource.CatalogId` (the other types write names). `ResolveGuid` in `References.psd1` swaps it for the catalog's name using the Id in the same export (`Read-PEExport`, carried to a delta export through a reference-only export of the parent type in `Export-PEDelta`); this is deliberate and small, and would go if DSC's export is fixed. `Url`, `AddedOn` and `AddedBy` of a catalog resource and the role-scope `Id` of a package are generated per tenant and are tenant-bound.
- **Approvers by object id (deliberate deviation, agreed 2026-10-23).** DSC exports the users of an assignment policy (approvers, requestors, reviewers) as user principal names and should turn them back into object ids when it applies the policy. In 2.26.1015.1 that did not happen for a policy created from a Revert (J-22: Mgx `ArgumentException: ObjectId`; the same configuration worked once the id was supplied). `Data\IdentityReferences.psd1` lists the user sets; when a Revert renders such a record, `Resolve-PEUserReference` looks each `singleUser` up in the target tenant with its Reader app (`New-PEUserIdResolver`, one match on the part before the `@`, as DSC's own lookup does) and renders the object id. A user that is not found keeps its name, so DSC fails on it as before. The blueprint, the stored records and the drift comparison are untouched (UPNs compare equal across tenants). Remove the entry when DSC resolves the name itself; worth reporting upstream.- **Not covered.** A group a catalog resource refers to must exist in the target tenant. Two access packages with the same display name in one catalog would make DSC's name lookup ambiguous. Other dependency chains (Intune assignments to groups, Conditional Access to groups) are not in `References.psd1`.

## Excluding Missing and Changed items in a replica

A tenant-specific object (this tool's own `M365DSC-Policy-*` apps, an Exchange Online app) is Missing or Changed in a replica for ever. **Exclude** now works on those in a **replica**: it records an `Unmanaged` decision for that tenant, and `Compare-PEState` sets State `Unmanaged` on a Missing or Changed finding when the decision names a tenant that is not `master`. The item leaves the drift counts, is never offered for Revert, and **Unexclude** on the Exclusions page brings it back. On the master Exclude still works only on target-only items (a Missing or Changed item there is real drift), the dialog says so, and a decision with no tenant, or for the master, never hides a Missing or Changed finding.

**Scope-level Revert and Promote.** The scope cards and the resource-type cards on the Overview now carry **Revert N…** (and, on the master, **Promote N…**) next to Check now, where N is the number of open Missing, Changed and TargetOnly items of that scope (`driftItems` in the tenant entry of `index.json`). They open the same dialog (config preview, reason, confirmation) and run the same job as ticking those rows on the Drift page and using the bulk button, so ordering, the per-item results and the replica rules all apply. Promote is not offered for a replica, as elsewhere.

## Ids that a Revert to another tenant has to get right

The blueprint keeps **names**. Where a GUID is needed to apply an object, the rule is: **if DSC accepts the name, send the name and look nothing up; look an id up only for the types we know need it, once per Revert, with DSC's own export.**

- **DSC takes the name (no lookup).** Intune assignments carry `groupDisplayName` beside `groupId` and DSC falls back to the name when the id is not found in the tenant (`M365DSCIntuneUtil.psm1`), so `Assignments.groupId` is ignored across tenants (`TenantBound`, global) and the name is compared and sent. Teams channels, tabs and teams carry `TeamName` (their group and team ids are tenant-bound). Catalog, package and policy references go by name (see the dependent-items section).
- **Stable global ids (nothing to do).** Application ids of Microsoft apps, role template ids, sensitive information type ids, permission grant ids: the same in every tenant.
- **The object's own Id is its DSC key (look up).** `OwnIds` in `Data\IdentityReferences.psd1`: `AADPermissionGrantPolicy` (readable ids such as `microsoft-user-default-legacy`) and `IntuneDeviceEnrollmentPlatformRestriction` (a tenant GUID). Their `Id` is kept in the record (blueprint v10). When a Revert goes to a tenant other than the blueprint's, `New-PEOwnIdResolver` exports the type from the target with the Reader app (once per type, DSC's own export) and `Resolve-PEOwnId` swaps in the Id of the object with the same key; when the target has none, the blueprint's Id is sent as it is (a create). The Id of the Intune type is tenant-bound for comparison.
- **Not covered yet.** A property that holds the GUID of another object and has no name beside it would need the same lookup (the group ids in authentication method policy targets are the likely first case; they are all-zero GUIDs in the demo data). Add the type to `OwnIds`-style data when one appears.
- **Still unrenderable:** `IntuneCustomizationBrandingProfile` (DSC's export omits the mandatory `DisplayName` of the default profile).

## Review against Microsoft365DSC (2026-10-24): what we use, what we deliberately do not

A review of our code against the pinned module (2.26.1015.1, class-based) for the thin-wrapper principle. Done: workload prefixes in one place (`Data\Workloads.psd1`, `Private\Workloads.ps1`; was five copies, `SC` was missing from some), one `Get-PEDscModuleFile` for the pinned module's data files. Deliberate gaps, so nobody re-investigates them:

- **`New-M365DSCDeltaReport` is not used.** It compares two config files per instance (HTML/JSON) and has no multi-tenant matching, rename detection, decisions or noise rules. `Compare-PEState` is that layer. DSC's per-property comparer (`Compare-M365DSCResourceState`, C# `ResourceComparer`) works on one desired and one current instance with a global drift list; a spike for the property diff of matched pairs is possible but our array-as-set and case-sensitive rules differ.
- **`CompareRules` (such as `IgnoreWhenPast`) are not readable offline.** `SchemaDefinition.json` carries only `ExcludedProperties` (78 resources) and `IncludedProperties` (12); the rules live in the resource class (`GetCompareParameters()`), so our one conditional ignore (`AADRoleAssignmentScheduleRequest`) stays in `Data\IgnoredProperties.psd1`. Open question for the owner: DSC's `ExcludedProperties` are properties its own Test ignores, so a Revert cannot fix a difference in them. Adopting them as ignore rules would reduce noise but also hide real settings (for example admin unit `Visibility`) and some are key properties (`SCUnifiedAuditLogRetentionPolicy` `Name`), so it is not done automatically.
- **DSC's relation templates are not an apply order.** `Modules\M365DSCRelationTemplates.json` (169 relations, which property names which resource) is broad and cyclic (a group "depends on" users, roles and service principals); ordering from it gave wrong depths (tried and reverted). `Data\References.psd1` stays the small explicit list a Revert needs.
- **Keys.** DSC declares keys as `[Key]` properties (`SchemaDefinition.json`). Of the 541 resources: 190 `DisplayName`, 94 `Identity`, 79 singletons, 64 `Name`, 20 `Id`, 41 other single keys, 53 composite. Of our 41 `KeyMap` overrides, 40 equal DSC's key (they exist because `Default` tries `DisplayName`, `Name`, `Identity` before the schema). Of the 439 types without an override or singleton flag, 364 already agree with DSC's key (or fall back to the schema) and 55 differ, mostly because our key is one part of DSC's composite (`AADGroup` is `DisplayName` here, `DisplayName` + `MailNickname` in DSC; `EXODistributionGroup` is `DisplayName`, DSC's key is `Identity`). Making resolution schema-first would change stored keys and so existing blueprints; not done.
- **Delta export filters (`Private\Delta.ps1`) stay.** They use DSC's own `Filter` lever (`Test-M365DSCResourceProperty` checks support); only the property that holds our key for `AADGroup` is ours.
- **`ExportLog.ps1` stays.** DSC tracks `ResourceStatus` per resource internally (`M365DSCReverse.psm1`) but exposes only counts (`-WithStatistics`), so per-component success is read from the console output. An upstream request to expose it would remove the parser.
- **FastHost compile engine is not used for apply.** Compile 9 s against 0.5 s, identical MOF for a valid config, but it silently drops a misspelt property (3.1.10); `-Engine Standard` validates names.

Decided after the review (2026-10-24):

- **Quick scan removed** (see "Known limits"), 460 lines.
- **Built-in roles.** Intune needs no list any more: a role flagged `IsBuiltIn = True` (set by the service, exported by DSC) is recognised by `RequireProperties` alone, which also covers roles Microsoft adds later. The Entra list (`AADRoleDefinition` template ids) stays: DSC exports no built-in flag for Entra roles, and a stale list only shows a little more noise, never hides drift. `tools\Update-PEBuiltInRoles.ps1` refreshes the Entra list only.
- **The plan registry and snapshots in `Private\Rectify.ps1` stay** (about 400 lines: frozen copies, fingerprints, the bounded configuration registry). They are our own safety rule, not DSC logic: what the user approved is exactly what is rendered, audited and applied once. The renderer and the AST check of the generated text are a real injection boundary, because the compile executes the generated file and its strings come from tenant data. If the size matters later, the first thing to try is keeping the snapshot as an immutable JSON string and hashing that; do it only with the tests of `Rectify.Tests.ps1` and `InvokeRectify.Tests.ps1` as the net.
- **DSC `ExcludedProperties` are not adopted as ignore rules** (see the section above): no noise from them has been seen in the live runs (147 of 171 types Reliable), so adopting them would hide settings without a proven benefit.

## Blueprint layers, and what a tenant is written from (2026-10-24)

Design: `docs/superpowers/specs/2026-10-24-tenant-vs-blueprint-gui-design.md`; plan: `docs/superpowers/plans/2026-10-24-tenant-vs-blueprint-gui.md`.

- **A tenant is only ever written from its own blueprint.** `tenants.json` keeps an ordered `Blueprints` list per tenant (master blueprint first, the tenant's own last); no list means the master blueprint alone. Two layers have screens and tests; a third layer is a longer list, not a redesign.
- **Layers are full copies, not overlays.** `Initialize-PETenantBlueprint` copies the master blueprint's latest version, or with `-FromCheck` starts from the tenant's own latest Full check (a baseline of what the tenant has, so the master layer shows the distance from master); `tools/Initialize-PETenantBlueprints.ps1` does the copy for every replica (no `-FromCheck` there yet). A blueprint that already exists is moved onto the tenant by promoting its differences (`Approve-PEBlueprintChange`). One tenant blueprint per tenant for now.
- **Three moves.** Promote (tenant to its own blueprint; the tenant's side wins, so an item the tenant lacks is removed from the blueprint), Promote up / Update tenant blueprint (blueprint to blueprint, `Move-PEBlueprintItem`, new version with a reason, refused when the target changed since the review) and Revert (blueprint to tenant, the existing Accept). Blueprint moves never write a tenant. No action applies the master blueprint to a tenant.
- **Promote from a replica with no blueprint of its own is refused** in the preview and in the worker: it would resolve to the master blueprint and change it without the master confirmation (found by the commit security review).
- **Drift against each layer** is the tenant's latest check state compared with that blueprint (`Get-PEGuiLayerView`), so no extra tenant read. A tenant checked before it got its own blueprint shows stored findings (old blueprint) next to the recomputed layer counts until it is checked again.
- **The GUI** reads `tenants/<id>/layers/<blueprint>/findings.json` (via `/api/tenants/<id>/layer-findings?layer=`) and `tenants/<id>/moves.json` (what each move would change, for the preview); the worker re-derives the real differences.
- Rename is only on the Tenants page (`RenameTenant`, `Set-PETenant -DisplayName`); the blueprint name is never renamed.
- Deliberate gaps: no screens for more than two layers; no tenant A against tenant B view; about 34 one-off inline styles remain in `app.js`.

## Why Security and Compliance reads fail in a full check (2026-10-25)

In a full check or Re-check every `SC*` type comes back NotChecked ("Connection to SecurityComplianceCenter failed earlier in this session: Object reference not set to an instance of an object"), in both tenants, although the same Reader app reads them when they are exported alone (10-23, and again 10-25). Not a permission or app problem.

- **Cause.** One `Export-M365DSCConfiguration` call runs every component in one process, in alphabetical order (AAD, EXO, Intune, SC, Teams; the order passed in is ignored). In that one process:
  - an Entra or Intune component (Graph) exported before SC makes the first SC connect fail inside the Exchange module (`ExoPowershellSnapin.NewEXOModule.ProcessRecord()`, null reference);
  - SC exported before Teams makes the Teams component fail ("`Connect-MicrosoftTeams` was found in the module `MicrosoftTeams`, but the module could not be loaded");
  - Exchange before SC is fine; SC alone is fine; Teams after a failed SC is fine.
  So one of SC and Teams (plus Graph before SC) cannot be read in the same process; DSC puts SC between them.
- **Reproduced** in 22 s with four components (`AADAccessReviewPolicy, EXOAcceptedDomain, IntuneWindowsHelloForBusinessGlobalPolicy, SCRoleGroup`) and with two (`AADAccessReviewPolicy, SCRoleGroup`).
- **Not the cause (each tried alone before a plain `Connect-IPPSSession`):** Graph connect, a Graph request, DSC's own `New-M365DSCConnection` for Graph then SC, the Graph shim, `M365DSC.mgx`, ReverseDSC, PSResourceGet, the export's global variables, `$ProgressPreference`. Only a real `Export-M365DSCConfiguration` of a Graph component leaves the process in a state where the connect fails; the exact mechanism is not identified.
- **Same family as** the LCM failure (issue 7563): both end in the Exchange module's connection code, so the LCM failure may be this conflict, not an LCM problem. Not tested.
- **Options, not done** (ours to discuss before any code, per the thin-wrapper rule): export SC in its own process (a second call of DSC's export, merged into one state; Teams could then follow in the main process), or leave SC check-only through a scope check, which runs it alone. A scope check of an `SC*` type already works for that reason (not run for this note).

### Fixed: Security and Compliance is exported in its own process (2026-10-25)

`tools/Export-M365DscTenant.ps1` splits the components (`Split-PEExportComponent`; the workloads flagged `OwnProcess` in `Data\Workloads.psd1`, today Security and Compliance) and exports them with a second run of itself, into `<output>\part-own-process`. `Merge-PEExportPart` then puts the resource blocks into the Node block of the main `export.ps1` and appends the part's `export.log`, so every reader of an export folder (full check, scope check, delta, blueprint add) is unchanged. The merge needs the layout Microsoft365DSC writes and checks that the merged file holds exactly the resource blocks of both files; otherwise it throws and changes nothing. A call with only SC components (a scope check of an SC type) is not split.

- Verified live with the Reader app: `AADAccessReviewPolicy, EXOAcceptedDomain, IntuneWindowsHelloForBusinessGlobalPolicy, SCRoleGroup, TeamsMeetingPolicy` in one tool call, all five Ok, 95 records through `New-PEStateFromExport`. Before: SC failed in the same call.
- Cleanup never fails an export: after the merge the part folder is deleted by `Remove-PEExportPart`, which retries for about ten seconds and then only warns. A first real run (Rob's tenant, 10 minute SC export, 17 SC types read) failed at this step because the freshly written `export.ps1` was still held by another process (probably antivirus or the indexer), although the merge had worked; the job reported "Export failed with exit code 1".
- Cost: one more process start and sign-in per export (about 20 s). A full check was not re-run for this change; Re-check a tenant to see the SC types read again.
- Retry (2026-10-26): one run lost 11 of 18 SC types because a reconnect threw "A task was canceled" and Microsoft365DSC then skips the rest of the workload (`M365DSCConnectionFailures`, "failed earlier in this session"). A clean re-run exported all of them, so it was transient. The tool now exports the SC part once more from scratch when its `export.log` reports `Failed exports` above 0 (`Test-PEExportPartFailed`) and merges the second result, failed or not.
- Deliberate gap: the Revert failure through the LCM (issue 7563) is not touched; it may be the same conflict and is untested.

The Activity page has a **Cancel** button on a queued job and on a running Recheck (`POST /api/jobs/<id>/cancel`, `Stop-PEGuiJob` in `gui/PEGui.psm1`).

- **Queued:** marked Cancelled at once and taken off `activity/active.json`. The worker moves a job from Queued to Running, and writes its final status, under the same lock the server holds to cancel (the two hash the same folder to the same mutex name), so a cancel is never overwritten and a job cancelled just before it starts is skipped (commit security review: that gap used to be open for a few milliseconds).
- **Running Recheck with a live worker:** the server sets `cancelRequested` on the job. The worker (`Invoke-PEGuiRequest`) sets `$script:PEJobCancelCheck` around each job; `Invoke-PEExportToolProcess` now starts the export as a child process that shares the console and asks that check twice a second. On a cancel it kills the child and everything it started (`Kill($true)`, so also the SC process) and throws `OperationCanceledException`; the job ends Cancelled, nothing is saved. Only a Recheck gets the cancel check at all; a job that changes things is never killed, and a stray `cancelRequested` on it does not turn its failure into Cancelled. Cancel arriving after the export (compare and GUI refresh, about two minutes) is too late: the job ends Succeeded.
- **Running job nobody is running** (worker closed, restarted, or busy with another job): the server marks it Cancelled itself, because nothing would honour a request. "Alive" means `activity/worker.json` (written by the worker on every pass and while an export runs: `pid`, `at`, `jobId`) names a running pwsh/powershell process, is at most 10 minutes old and names this job. This is the case of a job left Running by a closed worker; it also frees the Re-check button, which is disabled while any Recheck is Queued or Running.
- **Refused:** a running job that changes something (Revert/Accept, Connect tenant, Promote and so on): stopping it halfway could leave it half-done. Only a Recheck can be stopped while running. A finished job is refused too.
- A job the server marked Cancelled stays Cancelled if a late worker finishes it; a worker that fails after `cancelRequested` ends Cancelled, not Failed.
- Tested live on a copy of the data with a real Reader-app export: stuck job (cancelled directly), queued job (cancelled before it started), running Recheck (stopped within about a second, export process gone, no check saved), and the worker ran the next job normally. Workers started before this change write no heartbeat; restart the worker to get it.
- Known gaps: the Recheck button is disabled while any Recheck runs, so a second Recheck cannot be queued from the page; Cancel is not offered for the other long jobs (apply, connect tenant).


## Offline snapshots (2026-10-26)

A tenant the tool cannot reach (no app, no certificate, no network path) is registered as an **offline tenant** (`Set-PETenant -Offline`, or the "Offline tenant (upload files)" pill on the Tenants page). Its owner exports it with DSC (for example in a pipeline) and uploads the `.ps1` files; the tool compares them and generates configuration files the owner runs. Spec: `docs/superpowers/specs/2026-10-26-offline-snapshots-design.md`. Nothing here connects to the tenant, and Recheck is refused for it (`Tenant '<slug>' is offline: upload a newer export instead.`).

**The flow.** Upload (`UploadSnapshot` request, worker job) -> a Full check with `Meta.Source = Uploaded` -> optionally the first upload becomes the tenant's own blueprint -> drift against the layers the tenant follows -> decisions as for any tenant (leave as drift, move into a blueprint, exclude) -> **Generate configuration** (`GenerateConfig` request) writes two files and a manual list -> the pipeline owner runs them -> exports again and uploads again; the new check shows what changed.

**Version rule.** Every uploaded file must carry the pinned Microsoft365DSC version in its first line (`# Generated with Microsoft365DSC version <v>`; the pin is `Data\Versions.psd1`, `Get-PEPinnedVersion`). The server also checks that the file's `Import-DscResource -ModuleVersion` agrees with that first line. One file with another version, or none, or a disagreeing `Import-DscResource`, refuses the whole upload, naming the offending files and both versions; nothing is stored. The page checks only the first line in the browser (`VERSION_LINE` in `app.js`, the same rule as the server's first-line check); the `Import-DscResource` check happens on the server only. A leading BOM is tolerated.

**NotChecked for uploads without an export.log.** A pipeline export has no `export.log`, so a failed type cannot be told from an empty one. A type that has no records in the files is therefore NotChecked (no Missing claimed, so the generator creates nothing for it), not empty. A type with records is checked. "Type" here means a type of **any** blueprint layer the tenant follows (master first, own last), so the master layer view never reads an unuploaded workload as Missing either. A check compared with no blueprint (the first upload that seeds the own blueprint) marks none: `Initialize-PETenantBlueprint -FromCheck` copies a check's NotChecked list into the blueprint, where it would hide those types for good. When an upload is folded into an earlier check, a type of a **kept** workload that the earlier check never read (not in its records, its NotChecked list or the blueprint version it was made against, for example an item moved into the own blueprint after it) is NotChecked `not read by the earlier check`. The upload form offers a per-workload "these files are complete" option: for a ticked workload a type with no records is really empty, so blueprint items of that type read as Missing. Use it only when the export of that workload is known to be whole.

**Source and age per workload.** One check, but `Meta.Workloads` records for each workload whether its data was `Uploaded` or `Live`, and when. `Export-PEGuiData` writes this as `snapshot` on each tenant entry (a check made by `Invoke-PEFullCheck` has none and counts as Live at its export time). The GUI shows "Uploaded <date>" or "Exported live <date>", the oldest workload and its age, and each workload separately. Workloads not in a new upload keep their previous data, as in a scope check.

**Own blueprint.** A first upload can be saved as the tenant's own blueprint (`Initialize-PETenantBlueprint -FromCheck`). The upload is then read twice: the first check seeds the blueprint, and a second check from the same files holds the findings against it (a stored check is never rewritten). If seeding or the second check fails after the tenant and first check were stored, the job fails with a message that says so (tenant registered, check id stored, blueprint not seeded) and the tenant stays registered. A tenant with no blueprint of its own follows the master blueprint, and its check is compared with that.

**What the configuration targets.** The tenant's **own** blueprint (its last layer), the same as Revert. To align an offline tenant with a layer above (for example Production), first move the wanted items into its own blueprint with the existing move actions (PullDown, "update tenant blueprint"), then generate; an item moved into the own blueprint matches it and is not written. A tenant without an own blueprint cannot generate.

**What is written** (`New-PEOfflineConfig`, into `<GuiRoot>\configs\<jobId>\`):
- `Changes.ps1`: `PE_Changes`, Create for Missing and Update for Changed items. Run first.
- `Removals.ps1`: `PE_Removals`, `Ensure = 'Absent'` only for **Open TargetOnly** items of a type the own blueprint manages (at least one record of that type in it). An Open item counts as left as drift: nothing asks the user to confirm each removal, unlike Revert on a connected tenant, which needs a confirmed Remove decision. An item added to the blueprint, excluded or marked Unmanaged is never removed. Run second, after review.
- **Target-only items of a type the blueprint has no records of are never removed.** Nothing in the blueprint says the tenant should not have them (an own blueprint seeded from an Entra-only upload has no Exchange type, so every Exchange object would otherwise be deleted). They go to `Manual.json` with the reason "type '<T>' has no records in the blueprint, so nothing says the tenant should not have these; add them to the blueprint, exclude them, or remove by hand", and the job result says how many there are (`NoBlueprintTypeCount`). Whether "undecided = drift" is enough for any delete is an open question for the user.
- `Manual.json`: items the tool will not or cannot write, each with its reason.
- A file with no items is not written. Each file is written once and never overwritten; the job result carries the counts.
- **Findings are recomputed when generating** (`Compare-PEState` of the latest Full check's state against the current own blueprint and decisions), not read from the stored check, so a decision or a move made after the check is honoured. The GUI's findings list still shows the stored findings until the next upload, so counts can differ, in the safe direction.
- **Types the check never read are never created.** The check judged the types of the blueprint version it was compared with (and marked NotChecked what it could not show, including types of kept workloads its earlier check never read); a type added to the blueprint after the check counts as unread. If the blueprint version differs, the job result says which version was compared with which.
- **No Revert for an offline tenant.** The GUI offers no Revert (Accept) for its items, and the engine refuses an Accept request for it (`Tenant '<slug>' is offline: ...`) before recording any decision. Promote, Exclude and the moves work as for any tenant.
- **Refused:** a check patched by a scope check (`Meta.ScopeChecks`; which types it read cannot be told), a check whose blueprint version cannot be read, a check read from another tenant id than the one registered, and a tenant with no own blueprint. Upload a new snapshot (or run a full check) and generate again.
- Properties on DSC's ignored or secret lists are never written; an item that needs one goes to Manual.

**How the pipeline owner runs the files.** Each file starts with comment lines that say this too. Dot-source the file, call `PE_Changes -ConfigurationData .\ConfigurationData.psd1 -OutputPath .\Changes`, then apply with `Start-DscConfiguration -Path .\Changes -Wait -Verbose` (or the pipeline's usual DSC step); then the same for `PE_Removals`. `ConfigurationData` must hold `NonNodeData` with `ApplicationId`, `TenantId`, `CertificateThumbprint` and `OrganizationName` (and `TenantGuid` where the file uses it); the generated text references them and never holds a value. Changes before Removals. The module version in `Import-DscResource` is the pinned one.

**Deliberate gaps** (recorded, not hidden):
- DSC cannot create or remove every resource (a resource without `Ensure = Absent`, one that cannot be created from an export). Those items are listed as "needs manual action" with DSC's reason: that is DSC's limit, not ours. PossibleRename and Ambiguous findings are listed there too and never written.
- **Identity references.** The offline generator passes no identity resolvers (there is no tenant to ask for object ids), so types that reference users by UPN (for example `AADEntitlementManagementAccessPackageAssignmentPolicy`, UserSets) carry the UPNs from the blueprint. DSC 2.26.1015.1 fails on those and the item fails closed: it goes to Manual with the error and is never written in a form that would apply the wrong object. A real fix needs the owner's directory, which we do not have.
- **Size.** A generated configuration is refused above `PEMaxConfigLength` (8 MB) as a whole. When a file cannot be generated in one piece the list is split by halving down to single items (about 3 s per parse); items that cannot be generated go to Manual. A very large drift is slow. This differs from `Get-PEGuiRevertConfig`, which retries item by item.
- A request carries the file text in its JSON: at most 50 files, each name at most 200 characters. Pode's default body limit is 100 MB (a 10 MB upload was tried live). The worker reads a request file whole.
- The Manual list on the Activity page was not seen live with a non-empty list; it is covered by tests of the page source only.

**Data hygiene.** The uploaded export text is stored in `requests/<requestId>.json` and in `exports/<id>` (the check's export), and the generated files in `<GuiRoot>\configs\<jobId>\`. None of it is pruned automatically, and it may hold tenant data (names, UPNs, policy settings). Protect the data folder like the exports of a connected tenant, and delete old requests, exports and configs by hand when they are no longer needed.

## Overview and drill-down (2026-10-26)

Design: `docs/superpowers/specs/2026-10-26-overview-drilldown-design.md`; plan: `docs/superpowers/plans/2026-10-26-overview-drilldown.md`. GUI only; no engine or view-model change.

- **Overview top:** each tenant card has a row of workload cells (number = drifted, colour = drifted share of managed, grey `n/c` = not checked, `…` while loading). A Cards / Compare toggle (remembered in `localStorage` as `pe.overviewView`) switches to a matrix with one row per tenant and layer. Cells with drift open the Drift review for that tenant, workload and layer; a matrix column header opens the Drift review of that workload across all tenants (this can be more than four clicks from the top, deliberately).
- **Alignment by workload** sits above "Check by resource type"; each bar segment links on.
- **Workload page:** the kind legend rows link to the Drift review filtered by kind (the donut is a `conic-gradient` and cannot be hit-tested), and the per-type bars link to the type page.
- **Item page:** the "Show N identical" link is replaced by All / Drifted / Matching. It opens on Drifted when something differs, on Matching when nothing does.
- **Known approximation:** per-workload counts in `status.json` are against the tenant's own blueprint only. The master-layer cells are counted on the client from `layer-findings`, and their colour uses the tenant's managed count per workload as denominator, so the share is approximate (the tooltip says "of N managed").
- **Check by resource type drills down:** the type name and the drifted chip link to the type page (the chip to its Drifted filter), and the type page has its own Check now. The bulk buttons on the overview row stay (they already carry counts, e.g. Revert 5). The mock data has no `typeScopes`, so this card does not show in `-Mock`.

## Excluding a property for one tenant (2026-10-27)

Some differences are a policy the owner does not want enforced in one tenant, not noise everywhere. Example from the live read of Rob's tenant (`contoso`): `SCDLPCompliancePolicy.Priority` differs on all 5 policies the master and `contoso` share, because it is each policy's rank among that tenant's own policies. It stays **drift by default** (policies can be stacked, so order can matter) and nothing was added to `Data\IgnoredProperties.psd1`; the owner can exclude it per tenant instead. The rest of the Security and Compliance read (17 types, 602 records) matched: 14 sensitivity labels with no encryption differences, no tenant-own custom domains in the data (`tailspintoys.com` and `valorem.com` are the same in both tenants).

- **Decision kind `PropertyExcluded`** (`Set-PEDecision -Kind PropertyExcluded -ResourceType -Property -Tenant [-Key] -Reason`): `Tenant` and `Property` are required, `Key` is optional (empty = every item of the type), `Value` is unused. A rule without a tenant is ignored by the compare.
- **`Compare-PEState`** moves a matching difference of a matched pair from `Differences` to the finding's new `ExcludedDifferences` (same shape). A `Changed` finding with nothing left in `Differences` is kept with State `Unmanaged`: it is not counted as drift or offered for Revert, and it stays in the list so the item page can show it. With other differences left it stays `Open` and lists both. Top-level properties only (that is what `Differences` holds).
- **Revert** (`New-PERectifyPlan`, Update): an excluded property keeps the tenant's value in the planned record (left out when the tenant has none); the audit snapshot records `ExcludedProperties`. The finding's own blueprint record is not changed.
- **GUI:** the item page has **Exclude for this tenant...** next to each differing setting (scope: this item or every item of the type) and shows an excluded setting greyed as "excluded for this tenant" with **Bring back...**; the Exclusions page lists them. Requests `ExcludePropertyForTenant` and `IncludePropertyForTenant`; the worker records or removes the decision and compares the type's items with the tenant's own blueprint again from the stored snapshot (`Update-PECheckForItems`, no tenant read). Export: `findings.json` rows carry `excludedDifferences`, `exclusions.json` carries `propertyExclusions`.
- **Not done:** a nested path cannot be excluded (it stays a data-file rule); Selection list and bulk dialogs do not offer it; the item page's "Drifted N" filter count still includes excluded settings; an item that is both excluded as a whole (Unmanaged decision) and has excluded properties offers no Unexclude.
- **Ideas looked at and not built** (no evidence of a problem in the two tenants): suggesting noise rules from a check, ignoring `SCSensitivityLabel` `Encryption*` while `EncryptionEnabled` is off, mapping a tenant's own custom domains. Noise is a property of a resource type, so it is decided once from the data of a few tenants, not found again per check; revisit if a new tenant shows property differences that no rule covers.

## Standards blueprints (2026-10-27)

Design: `docs/superpowers/specs/2026-10-27-standards-blueprints-design.md`; plan: `docs/superpowers/plans/2026-10-27-standards-blueprints.md`. Engine and command line only; the GUI is the next step (mock-ups first).

- **What it is.** A standard is a blueprint folder plus `standard.json` (read-only marker, source, licence, imported versions) and `coverage\vNNNN.json`. The first source is ASD Blueprint for Secure Cloud (CC BY 4.0, attribution printed on import). `Import-PEStandard` parses the published DSC files with DSC's own parser (`Read-PEExport`), never runs them, and writes a new blueprint version per source release.
- **Real numbers (ASD v1.4.0, pinned module 2.26.x).** 133 settings in the seven files; 91 stored, 42 not covered: 25 use a placeholder (Entra Conditional Access 15, Security and Compliance 8, Exchange 1, Teams 1) and 17 use a property the pinned module does not have (Teams 6, Security and Compliance 5, other/SharePoint 3, Entra 1, Exchange 1, Intune 1).
- **Decisions.** Compare only what the standard states (`Compare-PEState -Subset`: records and properties it does not name are dropped from the target first). An item with a placeholder is left out whole, never half-filled. Accept risk is a decision kind (`RiskAccepted`: tenant, item, optional property, `ApprovedBy`, `Reason`, `StandardHash`); the tool is not the record of risk, so there is no expiry or evidence. A newer standard version that changes an accepted item reopens it with the hint "Accepted risk needs another look: the standard has changed."
- **Guards.** `Assert-PEBlueprintNotStandard` is called by Approve, Move (-To), Restore, Add-PEBlueprintType, Full and Scope checks, `Invoke-PERectify` and `Set-PETenant -Blueprints`. Nothing applies a standard to a tenant: promote with `Copy-PEStandardItem` into a blueprint, then Revert from that blueprint as usual.
- **Provenance.** Each stored record has `Provenance` (standard, source version in which its value was last set, control id). Copied records keep it.

Deliberate gaps, in the order I would take them:
1. Placeholder items (Conditional Access policies naming `$ConditionalExclude`, `$PrivUsers`, `$TermsOfUse`) are not checked; a per-tenant values file would lift most of the 25.
2. Teams `*Configuration` singletons carry `Identity = "Global"`, which the pinned module no longer has, and some Security and Compliance and SharePoint properties are also gone: not covered. Mapping old to new property names is DSC knowledge; raise it upstream or discuss before adding any.
3. No control IDs (ISM, Essential Eight): ASD's DSC files do not carry them; they exist only in the website's prose pages. `Provenance.ControlId` is empty.
4. SharePoint types are not exported by this tool's default workloads and the Reader app cannot read SharePoint; those items count as not readable.
5. `Copy-PEStandardItem` needs no master-write confirmation (same as `Move-PEBlueprintItem`; the GUI's two-step confirm is expected to cover it). An item the blueprint already holds identically is refused as "Nothing to copy" and so gets no provenance (reads as not adopted).
6. CIS benchmarks: no DSC-format source identified yet; NIST likewise. Not started.
7. The standard files were generated with older Microsoft365DSC versions (1.24.424.1 to 1.25.827.1); a property that is still valid but renamed is read as unknown, never guessed.

**Standards GUI design (approved 2026-10-27).** Mock-ups with example data: `docs/gui-mockups/standards.html` (open it in a browser). Four screens: Standards (loaded standards, coverage bar, per-workload table, new-release banner), Check against a standard (differences with Adopt and Accept risk, "Look again" for an acceptance the standard has since changed), Not covered (by reason), and the Accept risk dialog (approved by, why). Decisions: the standard-to-blueprint action is called **Adopt** (Promote already means tenant to blueprint); Adopt and Accept risk add to the Selection list like Revert, Promote and Exclude; "Accepted" gets its own teal status colour. Not built yet: it needs `Export-PEGuiData` to write standard checks and coverage, and worker requests for Adopt and Accept risk.
